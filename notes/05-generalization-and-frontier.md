# 05 — 泛化性、前沿对比与剩余空间

回答五个问题，全部基于本轮实验（lab/stress.py、experiments.jsonl 新增 20 余条）。

## Q1 我们跑的是什么数据集？泛化能保证吗？

**数据**：Amazon Reviews 2023（McAuley Lab, UCSD）Clothing_Shoes_and_Jewelry 类目的
冻结子集：50k 商品目录 + 200 条公开会话。会话从官方 **5-core leave-last-out** 划分
确定性采样；「对话」不是真实对话，是模拟器从目标商品元数据现场生成的。
私有测试 = 同分布的 800 条（不同用户、不同目标商品，场景配比相同 40/40/15/5）。

**三层泛化风险，逐层已验证：**

1. **统计抽样**（同分布新样本）：5 折分层 CV 折间标准差 0.0203，外推 800 条
   → 0.928 ± 0.005。风险低。
2. **热门度先验失效**：w_pop=0 时 score 0.867（-0.061）。但先验的成因
   （5-core 采样）在私有集同样成立（README 明说同一采样管线）。风险低。
   half_pop（w=2）仍有 0.925 —— 对权重本身不敏感，是平坦最优。
3. **模板改写**（官方保留加 paraphrasing 的权利）：这是唯一被实测证明的真风险。
   修复前 agent 在三种改写风格下掉到 0.776/0.807/0.671；加入模板无关的
   cue 解析 + 噪声/override 正则后恢复至 **0.918/0.923/0.856**（干净模拟器
   回归零损失，identity 风格精确复现 0.9280，harness 自身经过 bug 修复验证）。
   verbose 风格残余 -0.07，来自类目提取污染，已知、可继续收敛。

## Q2 与前沿相比：采纳了什么，舍弃了什么

| 前沿技术 | 决定 | 依据（实测/规则） |
|---|---|---|
| 多路召回（关键词+向量）| **舍弃向量路** | recall@200=1.000：词法召回已零漏召，向量路只能改变排序——而排序用特征更便宜 |
| Cross-encoder 重排 | 舍弃 | ~21 万次前向 CPU 不可行；线性特征重排已到 0.93 |
| LLM 语义排序（题面 Pillar I）| 舍弃主路径 | 断网条款不对称风险；保留接口可作可选增强 |
| RL 对话策略（CRM/EAR/UNICORN）| 舍弃 | 200 样本训不动 RL；且本模拟器最优提问是常数策略 |
| 信息增益提问（CPR/SCPR）| 部分采纳 | 作为待做的反事实实验保留（报告价值），非分数来源 |
| 热门度先验（工业排序标配）| **采纳** | 单特征 +0.114，全项目最大 |
| 结构化槽位状态（DST）| **采纳** | parse_message + override keep 策略 |
| 混合融合 RRF | 未用 | 只有一路召回，无需融合 |

一句话：**这是一个"检索已饱和"的问题，所以我们把全部复杂度预算花在排序特征
和状态管理上，而不是召回架构上** —— 每一次舍弃都有对应的测量数据。

## Q3 还有多少优化空间

score 0.9291（route-conditioned 后）。现实上界 0.9822。剩余 0.053：

- MRR 0.841 → 0.995 值 +0.046（占 87%）：57 个 rank 2–10 → rank 1
- HR 尾部 1 个未命中 + Eff 尾部：合计 ~+0.005
- **判断：边际递减已明显**（本轮 8 个新特征/变换只有 2 个为正，最大 +0.0033）。
  从 0.93 → 0.95 的代价可能是从 0.10 → 0.93 的总和。**建议冻结主线，
  剩余时间投入鲁棒性（verbose 残差）、报告与消融呈现** —— rubric 的 65%
  不看这个分数。

## Q4 更符合电商场景的设计

已实现并有效的：**按意图路由的差异化排序** —— browsing 加大热门度权重
（探索期用户没有明确约束，热门即相关），buying 保持约束精确匹配主导。
`route_overrides: {browsing: {w_pop: 6}}` → 0.9280→0.9291。增量虽小，
但这是真实电商检索的标准做法（query intent → ranking profile），
且是纯配置化实现，报告里是干净的一节。

方向正确但本模拟器不奖励的（写进报告的 discussion）：
价格/预算硬过滤（约束里 budget 出现 0 次）、多样性/MMR（评测只认唯一目标，
多样性纯粹费排名）、澄清问题的自然语言质量（模拟器只读 ask_attribute 字段）、
会话间个性化（profile 是常量+弱标签）。**评测指标与真实电商目标的错位本身
就是报告里 Innovation & Problem Insight 的素材。**

## Q5 不牺牲准确率的性能优化

实测延迟画像（云容器 2 vCPU，比 M 系 MacBook 慢）：

| 项 | 实测 |
|---|---|
| 目录索引构建（一次性）| 15.9s |
| 同进程二次实例化（缓存命中）| 0.2ms |
| turn 1（~4 terms）| 35ms |
| turn 3–4（~30 terms，饱和）| 64ms |
| 整个 4 轮会话 | ~207ms |
| token 消耗 | **0** |

已经比任何 LLM 方案快 2–3 个数量级。零成本可再取的：
1. FTS 查询串只取前 term_cap 个词——**延迟随词数线性涨**，评测下 term 累积
   有界（约束共 4 条），不是问题；真实部署下需要词预算策略
2. 噪声轮 terms 不变 → 复用上一轮排序（协议层面零风险缓存）
3. 索引落盘（file-backed sqlite）把 16s 构建摊销成 ~1s 加载——提交包启动
   体验用
4. 重排只对 100 候选做 dict 查找 + 浮点加权，~1ms，不是瓶颈

**判断：性能已过题目要求两个数量级，不再投入。** Feasibility 15% 的证据已充分
（0 token、CPU 单核、207ms/会话）。
